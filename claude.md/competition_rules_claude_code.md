> 사용 방식: Claude Code에게 이 파일을 먼저 읽게 한 뒤, 구현 파일·분석 코드·보고서·대시보드가 규정을 어기지 않는지 계속 참조하게 한다.

# 0. 대회 핵심 요약

## 대회 주제

**그래프신경망 기반 조직적 어뷰징 네트워크 탐지**  
**Graph Neural Network-based Systematic Abusing Network Detection**

대회의 핵심은 다음과 같다.

```text
YelpZip 원본 데이터셋을 활용하여
GNN 기반 조직적 어뷰징 네트워크 탐지 모델을 구축하고,
그 결과를 대시보드로 시각화하는 것
```

즉, 단순한 리뷰 텍스트 분류 문제가 아니다.  
핵심은 **리뷰 간 관계를 그래프로 구성하고, GNN을 이용해 조직적인 사기 리뷰 네트워크를 탐지하는 것**이다.

---

# 1. 대회에서 요구하는 문제 정의

## 1.1 왜 GNN인가?

공지에서는 기존 NLP 기반 텍스트 분석만으로는 사기 리뷰를 완벽히 탐지하기 어렵다고 설명한다.

사기 리뷰는 단순히 문장 하나가 이상한 문제가 아니라, 다음과 같은 **조직적 네트워크 문제**로 나타난다.

```text
한 사용자가 여러 개의 의심 리뷰를 작성
특정 식당/상품에 짧은 기간 동안 리뷰 집중
같은 별점 패턴이 반복
여러 계정이 비슷한 문장을 반복
특정 상품에 대한 평판을 조직적으로 조작
```

따라서 모델은 리뷰 하나의 텍스트만 보는 것이 아니라, 리뷰와 리뷰 사이의 관계를 함께 학습해야 한다.

---

## 1.2 GNN의 역할

GNN은 각 리뷰 노드가 주변 리뷰 노드의 정보를 주고받으며 학습한다.

공지에서 강조한 GNN의 장점은 다음과 같다.

```text
1. 개별 데이터가 아닌 조직적 패턴 포착
2. 주변 정보 전파를 통한 정확도 향상
3. 변칙적인 사기 수법에 대한 유연한 대응
```

따라서 이 대회에서는 GNN을 보조적으로만 쓰면 안 된다.  
반드시 **GNN이 핵심 모델**이어야 한다.

# 2. 메인 데이터셋 규정

## 2.1 사용 데이터셋

메인 데이터셋은 **YelpZip 원본 리뷰 데이터셋**이다.

공지에 따르면 YelpZip은 Yelp의 추천/필터링 시스템을 거쳐 수집된 약 60만 개 이상의 대규모 식당 및 비즈니스 리뷰 원본 데이터이다.

## 2.2 주요 컬럼

YelpZip 데이터셋의 주요 컬럼은 다음과 같다.

| 컬럼명 | 의미 | 활용 방식 |
|---|---|---|
| text | 리뷰 원본 텍스트 | 텍스트 임베딩, 대시보드 증거 자료 |
| user_id | 리뷰 작성자 고유 ID | R-U-R relation 구성 |
| prod_id | 식당/상품 고유 ID | 상품 중심 relation 구성 |
| label | 정상/사기 라벨 | 최종 예측 타깃 |
| date | 리뷰 작성 날짜 | 시간 기반 relation 구성 |
| rating | 별점 1~5점 | 별점 기반 relation, 노드 feature |
| tag | 추가 메타태그 | 보조 feature 또는 분석 참고 |

# 3. 라벨 변환 규정

## 3.1 반드시 지켜야 할 라벨 변환

YelpZip 원본 데이터는 다음과 같이 라벨링되어 있다.

```text
사기 리뷰: -1
정상 리뷰: 1
```

하지만 대회에서는 반드시 다음처럼 변환해야 한다.

```text
사기 리뷰 -1 → 1
정상 리뷰  1 → 0
```

## 3.2 구현 시 주의사항

Claude Code는 전처리 코드에서 반드시 아래 처리를 포함해야 한다.

```python
df["label"] = df["label"].map({-1: 1, 1: 0})
```

또는 이에 준하는 코드를 사용한다.

보고서에는 반드시 다음 문장을 포함한다.

```text
원본 YelpZip 데이터의 label은 사기 리뷰가 -1, 정상 리뷰가 1로 제공되므로,
본 연구에서는 모델 학습을 위해 사기 리뷰를 1, 정상 리뷰를 0으로 변환하였다.
```

# 4. 노드 및 그래프 구성 규정

## 4.1 노드 고정 규정

대회 규정상 노드는 반드시 **리뷰 단위**로 고정해야 한다.

```text
Node = Review
```

즉, 다음 방식은 메인 모델로 사용하면 안 된다.

```text
Node = User
Node = Product
Node = Business
```

Amazon 참고 데이터셋은 사용자를 노드로 하지만, 이번 대회의 메인 데이터셋인 YelpZip에서는 리뷰 노드가 기준이다.

## 4.2 엣지 구성 규정

GNN 그래프에는 반드시 다음을 포함해야 한다.

```text
기본 Relation 1개 이상
+
커스텀 Relation 1개 이상
```

즉, 최소한 2종류의 relation이 있어야 한다.

---

# 5. 기본 Relation 규정

기본 Relation은 아래 중 최소 1개를 포함해야 한다.

| Relation | 의미 | 구성 방식 |
|---|---|---|
| R-U-R | Review-User-Review | 같은 사용자가 작성한 리뷰끼리 연결 |
| R-T-R | Review-Time-Review | 같은 식당/상품에 대해 같은 기간에 작성된 리뷰끼리 연결 |
| R-S-R | Review-Star-Review | 같은 식당/상품에 대해 같은 별점을 준 리뷰끼리 연결 |

## 5.1 R-U-R

```text
Review_i.user_id == Review_j.user_id
```

같은 사용자가 작성한 리뷰끼리 edge를 만든다.

의미:

```text
동일 사용자의 반복적 리뷰 작성 패턴 탐지
```

## 5.2 R-T-R

```text
Review_i.prod_id == Review_j.prod_id
and same time window
```

같은 식당/상품에 대해 같은 기간에 작성된 리뷰끼리 edge를 만든다.

의미:

```text
특정 기간에 리뷰가 몰리는 집단적 조작 탐지
```

## 5.3 R-S-R

```text
Review_i.prod_id == Review_j.prod_id
and Review_i.rating == Review_j.rating
```

같은 식당/상품에 대해 같은 별점을 준 리뷰끼리 edge를 만든다.

의미:

```text
특정 별점으로 평판을 조작하는 패턴 탐지
```

# 6. 커스텀 Relation 규정

공지에서는 커스텀 Relation을 **창의성 평가 요소**로 본다.

커스텀 Relation은 참가팀의 도메인 지식과 아이디어를 바탕으로 직접 설계해야 한다.  
YelpChi나 Amazon의 relation은 참고 자료일 뿐이며, 그대로 따라만 하는 것보다 새로운 relation을 설계하는 것이 유리하다.

## 6.1 커스텀 Relation 설계 시 기준

좋은 커스텀 Relation은 다음 조건을 만족해야 한다.

```text
1. 사기 리뷰의 조직적 행동을 설명할 수 있어야 함
2. YelpZip 컬럼에서 계산 가능해야 함
3. 노드는 여전히 리뷰 단위여야 함
4. edge 수가 너무 폭발하지 않도록 top-k 또는 threshold를 적용해야 함
5. 보고서에서 논리적 근거를 설명할 수 있어야 함
6. 대시보드에서 증거로 시각화할 수 있어야 함
```

# 7. 샘플링 규정

## 7.1 반드시 먼저 샘플링 후 분할

대회 규정상 데이터는 다음 순서로 처리해야 한다.

```text
1. 원본 YelpZip 데이터에서 서브그래프 샘플링
2. 샘플링된 서브그래프 안에서 train/valid/test 분할
```

절대 아래 순서로 하면 안 된다.

```text
1. 원본 전체 데이터 train/test 분할
2. 그 뒤 일부 데이터 샘플링
```

## 7.2 무작위 샘플링 금지

단순 무작위 추출은 금지된다.

이유:

```text
무작위 추출은 노드 간 연결성을 파괴하여 GNN 학습을 불가능하게 만들 수 있음
```

따라서 반드시 그래프 연결성을 보존하는 서브그래프 샘플링을 사용해야 한다.

## 7.3 권장 샘플링 크기

공지에서 권장하는 서브그래프 크기는 다음과 같다.

```text
1만 개 ~ 5만 개 노드
```

CPU 환경에서는 2만~3만 개 리뷰 노드가 현실적이다.

## 7.4 권장 샘플링 전략

공지에서 제시한 전략은 다음과 같다.

```text
전략 A: 리뷰가 집중된 상위 N개 식당/Product 중심 추출
전략 B: 왕성하게 활동하는 상위 N명 User 중심 추출
전략 C: 특정 연도/월 등 특정 Time-window 중심 추출
```

우리 프로젝트에서는 세 가지를 결합한 전략을 사용한다.

```text
Product-User-Time Hybrid Dense Sampling
```

# 8. 데이터 분할 규정

## 8.1 분할 시점

반드시 서브그래프 샘플링이 완료된 후, 그 안에서 데이터를 분할한다.

## 8.2 분할 비율

공지 기준:

```text
학습용 80%
시험용 20%
```

train/valid 비율은 80% 안에서 자유롭다.

추천:

```text
train 64%
valid 16%
test 20%
```

## 8.3 재현성 확보

보고서에는 반드시 다음을 명시한다.

```text
random_state
샘플링 기준
train/valid/test 분할 비율
사용한 하이퍼파라미터
```

추천 고정값:

```python
RANDOM_STATE = 42
```

# 9. 모델 사용 규정
